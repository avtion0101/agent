## 1. 我们如何认真执行

路线图保留六个阶段：Python 工程 → LLM 基础 → RAG → 手写 Agent → LangGraph/MCP → 生产工程。训练围绕代码、实验、结果和解释展开。每一阶段需要交付物和验收证据；阅读完章节或到了某个日期，都不能自动进入下一阶段。

从今天开始采用以下流程：

1. 我提供当天概念、参考代码、独立练习、故障实验、答案和验收要求。
2. 你在自己的机器执行；提交关键输出、自己修改的代码、遇到的错误与解释。
3. 我检查行为、类型、边界和解释，指出具体缺口，并更新进度。
4. 通过当天关键要求后继续下一训练单元；没通过就修复或缩小任务。
5. 每七个训练单元做一次回顾：哪些能独立实现、哪些只能跟写、哪些仍不理解。

**助手写完参考代码，只代表材料交付。你能独立修改、调试、解释，才代表训练通过。** 不能替你声明已经掌握 Python、完成项目或具备岗位能力。

后续在对话中说“继续执行 Agent 计划”，并附上最新代码/输出或这份进度记录。每次根据可见验收证据续接；没有新证据时先复习或补验证，不按日历自动升课。

## 2. 当前事实与边界

你有 C/C++、Qt、工业软件、设备通信相关经验与学习经历，可以将字段协议、异常处理、事件循环和系统调试的经验迁移到 Agent 开发。这不等于这些方向已经达到高级水平，也不意味着你已具备 LLM 或 Python 的独立工程能力。

今天不需要云端 API Key、不需要 GPU，也不要求安装 LangGraph、Qdrant、Ollama。当前项目只使用 Python、uv、Pydantic、pytest 和 mypy。

本次实际检查发生在助手的 Linux / Python 3.12 环境。你自己的 Windows/macOS 环境仍需运行验证。我们尚未确认你当前主要开发设备、Python 版本或每天可用时间，不擅自修改你的机器或系统环境。

路线图是约六个月的学习目标，并非可以在一次对话内完成的学习成果。后期涉及云资源、付费模型、公开部署时，先形成可检查的实现与成本说明，再依据当时你的指令执行具体操作。

## 4. 六个阶段的交付与关卡

| 阶段 | 建议训练时间 | 核心交付物 | 进入下一阶段的依据 |
|---|---|---|---|
| Phase 0 Python 工程 | 3 周 | 日志分析 CLI、uv.lock、测试、类型检查、三项故障实验 | 本机检查通过，能独立加一个统计功能，解释 asyncio/GIL/校验边界 |
| Phase 1 LLM 基础 | 3 周 | Streaming CLI、结构化返回、用量与延迟记录 | 云端与本地分别验证能力，准确记录模型、token 计量来源、成本与失败行为 |
| Phase 2 RAG | 5 周 | 笔记问答、索引管线、≥20 条 golden dataset、检索和答案评估 | 对比基线与优化，有可复现实验数据，CI 可跑确定性检查与规定评估 |
| Phase 3 手写 Agent | 5 周 | 有工具协议的循环、限步/超时/预算、错误恢复、执行记录 | 稳定完成三种任务，解释失败点，危险操作有可检查授权流程 |
| Phase 4 框架/MCP | 5 周 | LangGraph 迁移、持久化/恢复、人工介入、MCP 集成 | 等价任务回归通过，恢复行为实测，SDK 版本组合已核对 |
| Phase 5 生产工程 | 5 周 | API、容器、tracing、eval gate、监控、成本/延迟报告 | 本地部署验收后按授权上线，外部访问实测；所有性能数字有原始记录 |

整个计划共约 26 周。这些是建议投入，不是死线。如果阶段验收不通过，持续补缺口；通过后可缩短重复训练。

Phase 4 先选择路线图方案 A：把 Phase 3 的 Agent 用 LangGraph 重写，便于用相同任务比较；再用小型 MCP Server 扩展。多 Agent 等单 Agent 基线稳定后才引入，并比较成本、延迟、共享状态冲突和真实收益。

从 Phase 0 开始建立确定性测试。Phase 2 起增加评估集和评估流水线；LLM judge 的费用、随机性和人工校准单独管理。测试与评估不互相替代。

## 6. 第一天：今天具体执行什么

完整讲解与练习见 `phase0-log-analyzer/docs/day01.md`。今天按顺序执行：

1. 下载、解压项目，进入 `phase0-log-analyzer`，确认 Python 和 uv 版本。
2. `uv sync --locked` 建立隔离环境。
3. 生成 10000 行日志并分析，核对 103 条坏行、9897 条合法行。
4. 运行 pytest 和 mypy；保留你自己机器的结果。
5. 阅读 `models.py` 和 `parser.py`，用自己的话描述文本如何变成可信的数据对象。
6. 自己写 `error_ratio` 函数；先做再看答案。
7. 至少运行数据校验故障实验，说明三个字段错误；如果有余力，再运行另外两个实验。
8. 提交输出、练习代码和解释，我据此验收 Day 1。

三项必做实验都已交付。它们不需要今天全部理解，在 Day 4/9/17 还会独立复验。

## 7. 版本和技术表述的执行校正

原文标记“2026 年已验证”，但附件没有提供对应证据链。不能把表格的精确版本、CVE、收购消息、岗位比例、所谓行业统一标准当作已核实事实。下面采用可执行规则，而不是替这些陈述补造依据。

| 原文中的风险表述 | 执行规则 |
|---|---|
| 具体版本/CVE/行业比例等没有随文来源 | 标为待核验；安装时查官方文档、发布记录、官方安全公告和当前依赖声明 |
| 换一个 base URL 就能切换所有后端 | 保持客户端抽象；分别核对模型名、密钥、streaming、tools、JSON schema、usage 与参数支持 |
| temperature=0 能排除随机性 | 降低采样随机性，有助排查，但不保证跨请求/后端完全相同；记录版本、参数和重复测量 |
| context/KV cache 把所有长输入问题归因到 O(n²) | 区分 prefill、逐 token decode、KV 大小、实现与硬件；用具体后端数据解释延迟 |
| async 并发解析大日志天然提速 | asyncio 管理协作和等待；CPU 吞吐单独做基准；线程/进程选择要有数据 |
| C++ 不会发生可变默认参数问题 | Python 的默认对象在函数定义时求值并被复用；C++ 普通值默认参数不同，但 static/共享引用一样能引入共享状态 |
| 输入过滤能解决 prompt injection | 过滤只是一个信号；执行层权限、路径范围、schema、授权与输出检查共同限制影响 |
| 移除 loop 上限做破坏实验 | 使用 mock 后端或仍保留外层硬预算，绝不进行无边界真实付费循环 |
| 24GB 显存模型推荐可以直接套用 | 到 Phase 1 才确认你的设备、显存/统一内存、量化、上下文和并发需求 |

当前只核对了 Phase 0 的官方资料。Phase 1–5 的库不提前安装、不宣称版本已确认。每次真实选型保存：日期、官方链接、版本/commit、依赖约束、实测命令、兼容性结果。
